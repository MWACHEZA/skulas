# QR Code Architecture, Threat Model & Key Rotation Procedure
**System:** Multi-Tenant School ERP SaaS (`skulas`)  
**Deployment Context:** Zimbabwe (Low bandwidth, frequent power cuts, offline tolerance required)  
**Cryptographic Engine:** Ed25519 (Asymmetric) & HMAC-SHA256 with tenant-isolated keys

---

## 1. QR Payload Specification

The payload follows a compact, versioned, signed format:
```text
v1:{TYPE}:{SCHOOL_CODE}:{ENTITY_ID}[:{EXTRA}][:EXP={yyyymmdd}][:KID={kid}]:{SIG}
```

### Components
- `v1`: Protocol version indicator.
- `TYPE`: One of `GATE` (gate admission), `FEES` (bursar payment slip), `LIB` (library book borrowing/returns), or `ATT` (classroom roll-call attendance).
- `SCHOOL_CODE`: Alphanumeric tenant identifier (e.g. `AX-GOXN5P`).
- `ENTITY_ID`: Student registration number, staff ID, or invoice ID.
- `EXTRA` (optional):
  - Fees slip: amount and currency (e.g. `150.00_USD`).
  - Library slip: book ID or ISBN (e.g. `BK-1049`).
- `EXP={yyyymmdd}` (optional): Expiration date in ISO `YYYYMMDD`. Scanners reject expired cards after 23:59:59 UTC of that date.
- `KID={kid}` (optional): Key Identifier pointing to the specific tenant keypair used for signing (enables zero-downtime key rotation).
- `SIG`: Base64url-encoded signature covering all fields before the final colon:
  - **Ed25519 (Primary / Offline PWA)**: 64-byte raw signature encoded as base64url (~86 chars).
  - **HMAC-SHA256 (Alternative)**: 16-byte truncated digest encoded as base64url (22 chars).

## 2. Threat Model & Mitigations

### Threat 1: Physical Card Photocopy or Smartphone Screen Replay
- **Attack Vector**: A student photographed a classmate's QR code or photocopied a physical student card to gain unauthorized gate admission.
- **Mitigations**:
  1. **Visual Photo Verification**: The Gate Scanner PWA prominently displays the student's high-resolution photo cached in IndexedDB. Guards compare the face on the screen with the student entering the gate.
  2. **Impossible Travel / Rapid Rescan Detection**: Any re-scan of the same student within 60 seconds triggers a `DUPLICATE_SCAN_SUSPICIOUS` alert flag in amber, logging the incident with device timestamp.
  3. **Direction State Machine**: Entry (`IN`) requires a subsequent departure (`OUT`) before another `IN` is permitted, preventing multiple students from queuing behind one QR code.
  4. **Optional Rotating App Tokens**: For student smartphones, the student portal can generate short-lived dynamic QR tokens refreshed every 30 seconds.

### Threat 2: Cross-Tenant Card Replay (School A Card at School B)
- **Attack Vector**: A student from School A attempts to scan their ID card at School B's gate.
- **Mitigations**:
  1. **Strict Tenant Isolation**: Scanner devices are locked to their own `SCHOOL_CODE`. Payload parser verifies that `payload.schoolCode === currentSchoolCode`. Any mismatch immediately returns `TENANT_MISMATCH` and `CROSS_SCHOOL_FORBIDDEN`.
  2. **Independent Cryptographic Keys**: Each school maintains unique cryptographic keypairs. School B's public key mathematically cannot verify a signature generated by School A's private key.

### Threat 3: Scanner Device Theft in Offline Mode (Zimbabwe Power Cut Scenario)
- **Attack Vector**: Guard's mobile phone or tablet is stolen, lost, or extracted via ADB while operating offline at a remote gate.
- **Tradeoff Analysis (Ed25519 vs HMAC-SHA256)**:
  - **HMAC-SHA256 (Symmetric)**: The shared secret must be stored on the client device (e.g., IndexedDB or localStorage). If the device is compromised, an attacker can extract the secret and forge unlimited valid student cards for that school.
  - **Ed25519 (Asymmetric - Implemented)**: The client device holds **ONLY the tenant's public key** (`spki`). The private signing key resides strictly on the backend server. If a device is stolen, the attacker gains **zero forging capability**; the device is verify-only.

### Threat 4: Data Tampering on Payment Slips
- **Attack Vector**: Student alters the fee amount on a paper slip from `$50` to `$500`.
- **Mitigation**: The signature covers the entire canonical string `v1:FEES:SCH001:STU123:50.00_USD:...`. Modifying even a single character invalidates the cryptographic signature verified via `crypto.timingSafeEqual`.

## 3. Key Rotation Operational Procedure

Key rotation allows schools to revoke compromised keys or roll over keys annually without invalidating already-printed plastic student cards.

### Operational Steps
1. **Trigger Key Rotation**:
   An authorized administrator executes key rotation:
   ```http
   POST /api/qr/rotate-keys
   Authorization: Bearer <Admin_JWT>
   Content-Type: application/json

   {
     "graceDays": 30
   }
   ```
2. **Automatic Lifecycle Transition**:
   - The server marks all current active keys as `isActive = false` and sets `expiresAt = now() + graceDays` (30 days).
   - A new Ed25519 keypair is generated with a unique key ID (e.g. `k_mvl3ie0w`).
   - The new key is marked active for subsequent card issuance and batch generation.
3. **Card Rollover During Grace Period**:
   - Cards issued under the new key bear `KID=k_mvl3ie0w`.
   - Cards issued under older keys bear their respective `KID` tag.
   - When verifying scans (`POST /api/verify` or offline PWA), the verifier resolves the key corresponding to `KID`. If the key is within its 30-day grace period, the card continues to authenticate cleanly.
4. **Offline Manifest Auto-Update**:
   - Guard devices automatically download the updated tenant manifest on network reconnect, updating the public key ring in IndexedDB.
5. **Decommissioning**:
   - After 30 days, old keys expire and are rejected, requiring any unrenewed physical cards to be re-printed.
